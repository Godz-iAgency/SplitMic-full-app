# SplitMic — Progress & Roadmap

_Austin-focused music-industry connection platform for bands, venues, talent buyers, record labels, and festivals. Content (shows, venues, directory) is Austin-only; membership is open to anywhere in Texas — see §2 #16._

Last updated: **2026-08-14**

For setup and a codebase tour, see [`README.md`](README.md). For the
engineering standards that apply to changes here, see [`CLAUDE.md`](CLAUDE.md).
For the database schema gap (some legacy tables with no migration file), see
[`migrations/SCHEMA_HISTORY.md`](migrations/SCHEMA_HISTORY.md).

## 1. Status at a glance

### ✅ Done (built, wired end-to-end)

- **Auth** — Google OAuth + email/password (sign up, sign in, forgot/reset password).
- **Onboarding** — 3-step flow: player type → Texas address (street + city + ZIP, validated client-side against `lib/address/texas.ts`) → player-type-specific profile form (all 5 types). Photos/video happen immediately after on `/profile/edit`, which auto-publishes on save. A pre-signup mini profile builder (genres + one scale question) on the landing page carries answers through signup so onboarding starts pre-filled.
- **Profiles** — full public/owner profile view, photo/video upload with cropping/compression, Band Readiness Score, one-click Publish/Unpublish toggle at the top of the page (in addition to the existing bottom-of-page publish cards).
- **Discover / Search** — filter by type, genre, sort, text query; pagination; category tiles; Band Readiness scoring baked into band cards.
- **Marketplace / Opportunities** — post events, opportunities, and open mics; band tagging on events (accept/decline/share-to-feed); respond/apply flow; full owner CRUD.
- **Open mic signups** — bands sign up for a venue's open mic; venue gets a roster dashboard, can reorder the running order, and check bands in/mark no-show (`app/opportunities/[id]/roster`, `signUpForOpenMic`/`reorderOpenMicSignup`/`setOpenMicSignupStatus` in `app/opportunities/actions.ts`).
- **Connections & Messaging** — Connect requests, accept/decline, 1:1 DM threads, unread badges, inbox with Requests / Conversations tabs.
- **AI show-matching for talent buyers** (`/match`, talent-buyer accounts only) — plain-English show description → Gemini extracts genre/draw/band-size/vibe criteria → ranked against published bands using our own data. Gemini never ranks or sees band data directly; a "why matched" line and Connect button sit on every result. Degrades to ranking by profile completeness if Gemini is unreachable, with that stated in the UI. See `lib/ai/`, `lib/supabase/matchBands.ts`, `app/match/`.
- **Admin console** — dashboard stats, user moderation (suspend/delete/publish), post moderation, connection audit, full action log.
- **Notifications (email)** — Resend transactional email for connection requests, post responses, and new messages, each deep-linking to the specific thread/request rather than a generic inbox (`buildCtaPath` in `lib/notifications/email.ts`).
- **Scheduled cleanup of expired posts** — `GET /api/cron/cleanup-posts`, secret-guarded, dry-run supported, batched, idempotent. Posts soft-expire from the Feed after 7 days (unchanged) and are hard-deleted a **year** later. The long window is deliberate: `event_band_tags` and `open_mic_signups` cascade with the post, so it is the only place a show's history lives. Retention under 30 days is rejected outright. Scheduled weekly via `vercel.json`; portable to any scheduler.
- **PWA** — installable, custom install prompt, offline fallback page, service worker (production only).
- **Public landing page** — hero, features, how-it-works, player-type explainers, support/contact form.
- **Business directory (`/directory`)** — public, no-login guide to Austin's music industry across 8 categories, one indexable page each at `/directory/<slug>`. Cards carry each business's Open Graph preview photo or a website screenshot (or a category-themed fallback until either is captured), a favicon-derived logo, a clickable subcategory chip that refilters, and Website/Directions/Reviews/Share actions — Directions and Reviews are Google Maps searches by business name, so they need no stored address. Filter bar has a live result count and a subcategory dropdown populated from the data. 584 businesses imported from a scraped CSV via an admin screen (`/admin/directory`) with a dry-run mode. Tiered listings (standard/featured/spotlight) drive both sort order and visual treatment, so it reads as a curated guide rather than a dump. Built-in outreach tracker (status + notes + last-contacted, including `do_not_contact`) — this is the tool the 584-business outreach campaign actually runs from. Scraped listings can be linked to real SplitMic profiles as businesses sign up (`claimed_profile_id`), which is the conversion path. Re-import is idempotent and never overwrites hand-set tiers or outreach state (regression-tested). Scraped emails and the outreach pipeline are blocked from the public role by column grants, not just RLS. `ItemList`/`BreadcrumbList`/`FAQPage` JSON-LD per category. A free website liveness check (`lib/directory/websiteCheck.ts`) confirms each listing's site still responds — only a non-resolving domain, refused connection, or hard 404/410 counts as dead, so a flaky moment never wrongly flags a real business; the admin panel can auto-run the check across every remaining listing and then hide (not delete) the confirmed-dead ones, reversible from the row toggle. See `lib/directory/`, `app/directory/`, `app/admin/directory/`.
- **Live events (`/live`)** — public, no-login page listing Austin live music happening today/this week, aimed at "Austin live music" search traffic. Events scraped daily from Do512 via Firecrawl (`lib/events/do512.ts`), cross-referenced against SplitMic's own published bands/venues so a card can link straight to a real profile (`lib/events/matching.ts`), stored in `live_events` (public read, service-role-only writes). Each event links out to Google Maps directions and an Uber deep link, no API key needed for either. Page carries a 10-question FAQ and `MusicEvent`/`FAQPage` JSON-LD built from the same content it renders. Scheduled via `GET /api/cron/sync-events`, same bearer-secret pattern as cleanup-posts (now shared via `lib/http/cronAuth.ts`), fails closed if unset, skips its own deactivation step on a partial scrape so a transient Firecrawl hiccup never wipes real listings.

## 2. Decisions locked (still in effect)

| # | Decision | Choice |
|---|----------|--------|
| 1 | AI provider for show-matching | **Gemini API** (`gemini-2.5-flash`, plain `fetch` against the REST API, no SDK dependency) |
| 2 | AI matching depth | **Structured extraction → existing search filters.** No embeddings / vector DB. |
| 3 | Open mic signup model | **Simple ordered list.** First-come-first-served; venue can reorder + check in. No time-slot picker. |
| 4 | Email work | **Deep links to the specific thread/request/post.** Domain verification remains a manual ops task. |
| 5 | AI fallback provider | **None.** Considered wiring `OPENROUTER_API_KEY` as a backup LLM if Gemini is down; decided the existing graceful degrade (rank by profile completeness, tell the user) already covers it, and a second provider isn't worth the added surface for a rare failure mode. |
| 6 | Post retention | **1 year** past soft expiry, then hard delete. 90 days was considered and rejected: at current scale the storage difference is nil, and a shorter window would destroy show history before a future "shows played" profile feature could ever use it. Easy to tighten later; impossible to un-delete. |
| 7 | Show history storage | **Stays on the post for now.** There is no separate archive — `event_band_tags` / `open_mic_signups` hang off `marketplace_posts` and cascade with it. A real "Memories"-style permanent history on band/venue profiles (surviving post deletion) is a **separate future feature**, not part of cleanup. |
| 8 | Live-events data source | **Do512, not Bandsintown**, despite the feature originally being scoped around Bandsintown. Bandsintown's self-serve API is artist-scoped (`GET /artists/{name}/events`), not city-scoped — it can only answer "what shows does band X have," not "what's happening in Austin tonight," so it can't drive a real citywide feed. Do512 runs an actual dedicated Austin live-music-today page. Bandsintown may still be worth adding later, narrowly, as a "your upcoming shows" block on an individual band's own profile — not as the /live feed's source. |
| 9 | Directory re-import safety | **Partitioned insert / update-scraped-fields-only / unchanged, never a blanket upsert.** A plain upsert would wipe hand-set tiers and the entire outreach pipeline on every re-run — the highest-risk defect this feature could have shipped. Guarded by a test that fails if any curation field enters an update payload. |
| 10 | Directory email exposure | **Column-level `GRANT`, not just RLS.** RLS is row-level; the public anon key can query PostgREST directly for any column of a readable row, which would expose 445 scraped contact addresses and the private outreach notes. `migrations/step11_business_directory.sql` revokes the blanket grant and re-grants only public-facing columns. Don't remove that block. |
| 11 | Directory route shape | **`/directory/<category>` real paths**, not `?category=`. Eight separate indexable pages each targeting its own search term beats one page with query params, which search engines treat as near-duplicates. |
| 12 | Directory card imagery | **Three sources, tried in order: Open Graph image → Firecrawl website screenshot → brand gradient.** The scrape captured no images at all. All three are free — a Google Places photo pipeline (a real venue shot) was built and then removed: its API is billed, and its photo URLs expire and need periodic re-fetching, which contradicts a one-time backfill. The OG image is each business's own link-preview photo, pulled with a plain fetch, no key, no cost. `migrations/step13_directory_places.sql` and its `places_*`/`place_photo_*` columns are left in place unused rather than dropped — same treatment as the step2/step3 schema gap. Logos are separate — derived from each site's favicon at render time, nothing stored. Both remaining photo pipelines are batched and resumable; a row is never re-attempted once checked. |
| 13 | Page titles vs. the "Austin live music" keyword | **`/live` = "Austin Live Music Tonight", `/directory` = "Austin Live Music Directory".** Titling both plainly "Austin Live Music" (as first requested) would have had them compete for one phrase and split the ranking signal. Both carry the keyword against different intent instead. |
| 14a | Trusting LLM-extracted scrape output | **Never trust extraction from a page that didn't return 2xx.** Found live: Do512's `/this-week` began returning 500, Firecrawl scraped the error page anyway, and the LLM invented well-formed concerts to satisfy the schema — Taylor Swift at MetLife Stadium, Billie Eilish at United Center, 2023 dates. Nothing downstream could tell those from real rows. Two guards now: `scrapeDo512Events` rejects any scrape whose `metadata.statusCode` isn't 2xx, and `mapEventToRow` rejects dates more than `MAX_EVENT_DAYS_AHEAD` (60) out, since a "today"/"this weekend" listing can't legitimately contain one. Both are regression-tested. The lesson generalizes to any future LLM extraction: a schema-shaped response is not evidence the source had data. |
| 14a-3 | Scraping a URL whose content changes but whose path doesn't | **Always `maxAge: 0` on the Do512 scrape.** Firecrawl caches by URL. `…/events/live-music/today` is the same URL forever while its content turns over daily, so a cache hit re-serves the *previous* day's listings. In production this meant the 9am sync ingested the prior evening's page, every event was already in the past, all were filtered out, and the feed wrote zero rows — while reporting `{eventsScraped: 16, eventsUpserted: 0}`, which looks like a healthy quiet night. Two changes: force a live fetch, and add `eventsSkippedPast` to `SyncResult` so "stale source" is distinguishable from "nothing on tonight" at a glance. Note this is the opposite call from the directory screenshot job, where caching is *desirable* — a business's homepage rarely changes and a cache hit saves a credit. The rule is about whether the URL's content is time-bound, not about caching being good or bad. |
| 14a-4 | /live cards without a real destination | **Superseded twice — see below.** Originally shipped as "no link, not a generic Google search," then reversed after seeing it live: an unclickable card among clickable ones reads as broken, not as "no data available." The first fix linked every unmatched card to a Google Maps *name search* for the venue — but that's not really "the venue," and a name-only search can resolve to the wrong place. Reworked again: unmatched cards (`VenueLinkOverlay.tsx`) now open a small in-card chooser — "Google Maps" / "Get an Uber" — instead of silently opening a weak search tab, framed honestly as wayfinding rather than a fake venue page. Matched cards (SplitMic profile or directory listing) still link straight to that real page. The two URL builders are shared (`lib/events/getThereLinks.ts`) between this chooser and the always-visible Directions/Uber buttons, so there's one definition of "the venue's destination," not two. Known rough edge, unchanged: a handful of Do512 rows carry a town name instead of a venue name (e.g. "Luckenbach, TX"), producing a slightly odd but harmless destination string. Not worth a special case for the rare out-of-Austin show. |
| 14a-5 | No-photo card image | **Superseded — see below.** An abstract glow/pattern treatment (ported from the directory's `BusinessCard` fallback art) was tried first and shipped, then swapped for the directory's own generic Venues photo (`CATEGORY_META.venue.image`), then swapped again for a dedicated asset once it was clear reusing the Venues-tile photo across many unrelated no-photo venues read as a mismatch with the landing page. `EventImageBand.tsx` now points at `/live/fallback.jpg`, a photo generated specifically for this "no info available" case (concert crowd silhouette against stage lights — matches the feed's own visual language instead of borrowing the directory's). Always renders an `<img>` (real photo or the generic one), no separate no-image branch. |
| 16 | Membership boundary vs. content boundary | **Signup widened from Austin-only to any Texas address; everything the app *shows* stays Austin-only.** These are now deliberately two different boundaries. Real musicians who play the Austin scene but live in San Antonio, San Marcos, Houston etc. were blocked at signup by a ZIP gate — the app was turning away exactly the people it exists for. The rule now lives in one place (`lib/address/texas.ts`), imported by both the onboarding step and the address-validation route so they can't drift. **Content deliberately did NOT change**: /live still scrapes only Do512 (Austin), the directory is still Austin businesses, SEO still targets Austin keywords. A member in Houston sees the Austin scene — that's the product, not an oversight, and someone in Austin must never get a San Antonio show in their feed. This was safe to do narrowly because *nothing about the content pipeline derives from a user's own address* — verified before changing anything. Three things did have to change beyond the ZIP range, all of which would have silently corrupted data: (1) `city` was a hardcoded `"Austin"` string *and* a TypeScript literal type, so a Houston member's row would have claimed Austin — it's now a real required input; (2) `OnboardingFlow`'s resume path rehydrated a saved address with a hardcoded `"Austin"`, which would have overwritten a returning out-of-town member's real city; (3) the signup and login pages both promised "verify a physical Austin, TX address," which would have turned away the intended new members before they ever reached the form. **Also corrected a pre-existing doc inaccuracy found while verifying**: both README and PROGRESS described onboarding as "Google-Maps-validated," but `/api/validate-address` has zero callers — the live check is client-side. That route is kept (it's the stricter check — it confirms a street actually exists, which a ZIP range can't) and was updated in lockstep so wiring it up later can't silently restore the Austin-only rule. **Follow-up:** `buildDefaultBio` (`app/profile/edit/page.tsx`) also hardcoded "Austin" into every auto-generated bio, so a Houston band's suggested bio would have read "Austin Rock act." It now uses the member's own city, falling back to "Austin" only for rows saved before city was required — which is not defensive theatre: production has a real `city = NULL` row that hits it. Verified against live data rather than assumed: of 9 profiles, only 3 have a never-set bio (the sole case this function fires for), and all 3 resolve to "Austin" either explicitly or via the fallback, so no existing member's bio text changes by a single byte. |
| 17 | Ticketmaster as a second live_events provider | **Provider-agnostic row shape, not a plugin interface.** "Provider architecture" turned out to mean: every provider module (`do512.ts`, `providers/ticketmaster.ts`) maps its own raw shape into the exact same `LiveEventInsert` type, and the shared match/upsert/deactivate pipeline (`upsertProviderRows` in `sync.ts`) never branches on which one produced a row. A future Eventbrite provider is a third file following that shape, not a change to the pipeline. The frontend requirement ("shouldn't need to know the source") was already true before this — `EventCard`/`GetThereButtons`/etc. never referenced Do512 — so the only place `source` is inspected at all is `lib/events/dedupe.ts`, in `lib/`, not a component. |
| 17a | Deactivation had to become source-scoped — this is not optional | **The correctness fix this architecture actually required.** The original single-provider deactivation logic said "deactivate any active future row absent from this run's result set." Reused unscoped across two providers running on independent schedules, every Ticketmaster sync would have deactivated all of Do512's rows, since Do512 rows never appear in Ticketmaster's own scraped result. Fixed by adding `.eq("source", source)` to the deactivation query. Regression-tested twice (once per provider's sync function) by temporarily removing the scoping and confirming both tests fail — this is exactly the kind of bug that looks like nothing changed in dev (an empty local table has nothing to wrongly deactivate) and only shows up against real data. |
| 17b | Cross-provider duplicate prevention | **A non-destructive read-time pass (`dedupeAcrossProviders`), not sync-time.** The two providers run on independent schedules (Do512 daily, Ticketmaster every ~4h), so a Do512 row synced at 9am and a Ticketmaster row synced at 1pm are never in memory together during either sync — the only place both are visible at once is a read of the already-stored table. Matches same-venue/same-artist (fuzzy, reusing `namesLikelyMatch`) within a 3-hour window, and when both exist, keeps the Ticketmaster row (real ticket URL, real event id, genre) over Do512's. Nothing is ever deleted or deactivated by this — a wrong duplicate guess hides a card for one request, never loses data, which is what "prevent duplicate listings without accidentally deleting legitimate events" actually required. |
| 17c | "Paid" filter means "not confirmed free," not "confirmed not-free" | A literal reading (`isFree === false`) would have left the Paid filter nearly empty: Ticketmaster rows always have `isFree = null` (never guessed at — Ticketmaster's Discovery API has no reliable free/paid signal on the base event object, and guessing would be exactly the kind of unvalidated assumption this codebase's External Data principles warn against), despite being real ticketed shows. "Free" stays strict (`isFree === true` only) since that's a claim worth getting right — showing someone a "free" show that charges at the door is worse than under-filtering. Logic lives in `lib/events/filters.ts`, unit-tested directly rather than only reachable by clicking through the page — same pattern as `isToday`/`isUpcoming` in `time.ts`. |
| 17d | Vercel Hobby caps cron at once/day — confirmed, not assumed, before designing around it | The brief asked for a ~4-hour Ticketmaster sync cadence. Checked directly against Vercel's docs before building anything: Hobby-tier cron jobs are hard-capped at once per day; a more frequent schedule fails at deploy time, not silently. `/api/cron/sync-ticketmaster` is deliberately scheduler-agnostic (same `Authorization: Bearer $CRON_SECRET` pattern the Do512 route already used, which itself was already documented as "any service that can send that header" before this feature existed) so a free external trigger — `.github/workflows/sync-ticketmaster.yml`, GitHub Actions, `0 */4 * * *` — delivers the real cadence without a paid Vercel plan. Same 60s function budget still applies regardless of caller, which is why `providers/ticketmaster.ts`'s `TIMEOUT_MS`/`MAX_PAGES` are tuned the same way Do512's were (§ #14a-10) — except these numbers are a conservative starting point, not empirically measured against the real API, since no `TICKETMASTER_API_KEY` was available while building this. Revisit once real timings are known. |
| 15 | Touch feedback and motion system | **One `.tappable` definition in `globals.css`, applied broadly — not a scale value copy-pasted per button.** The app is an installed, touch-first PWA whose interaction feedback was almost entirely `hover:`, which barely fires on touch: pressing a button gave no response until navigation completed. `.tappable` (press scale 0.97, 100ms ease-out) and `.tappable-lg` (0.99, for full-width surfaces where the same ratio travels far more pixels) now cover ~70 controls, applied to the shared `.btn-primary`/`.btn-secondary` and via mechanical replacement of the three repeated pill patterns. Three supporting decisions: (1) `-webkit-tap-highlight-color: transparent` kills the mobile browser's own grey flash, which otherwise fights the press scale — but since that removes feedback from *everything*, a floor rule dips opacity on any interactive element not already handling its own press, so no control is left silent; (2) `touch-action: manipulation` on controls drops the legacy ~300ms double-tap-zoom delay, which sits directly on the input path; (3) `.card-pressable` uses `:has(> a:active)` for cards whose click target is a transparent stretched overlay — the overlay has nothing to dim, so the press must be reflected by the card behind it, and the child combinator is what keeps pressing "Directions" from depressing the whole card. **Composition gotcha, recorded because it silently degrades rather than breaking:** Tailwind emits utilities after components, so a literal `transition` utility on the same element overrides these classes' timing — the scale still applies, just at 150ms. Where both were needed on one element (`.btn-primary`, `.card-pressable`) the transition is declared once instead. |
| 15a | Reduced motion | **Narrowed to non-vestibular properties rather than killed wholesale.** The previous backstop forced every transition to `0.001ms`, which is compliant but treats reduced motion as "no feedback" when it means "gentler feedback" — a colour or opacity change carries meaning and triggers no motion sensitivity, while travel and scaling do. Keyframe animations are still snapped to their final frame (they're the actual hazard, and this guarantees nothing is stuck mid-animation), but transitions now survive at 120ms restricted to opacity/colour/shadow. Transform feedback still *applies*, it just arrives instantly — so a press stays legible without animating movement. Also added the two signals that had zero coverage: `prefers-reduced-transparency` and `prefers-contrast` both make the translucent chrome opaque, targeted via the `backdrop-blur` utilities so future translucent surfaces are covered without opting in. |
| 15b | Chrome, overlays, and why not framer-motion | **Sticky translucent header matching `LandingNav`'s existing treatment**, so the signed-in app and marketing site read as one product; the background is load-bearing, not decorative, since content passes under a bar that no longer scrolls away. Verified empirically that `body`'s `overflow-x-clip` does not break `position: sticky` (`clip` doesn't create a scroll container the way `hidden` does) rather than assuming it. `VenueLinkOverlay` gained Escape-to-dismiss, outside-click, focus-in-on-open and focus-restore-on-close — it previously had no keyboard exit at all, which was an accessibility gap, not just a polish one. Motion is **CSS keyframes, not framer-motion**, even though that library is already a dependency: it's currently only pulled in on the landing page, and /live is a public SEO page where ~30KB for one popover isn't a fair trade — confirmed post-change that /live's First Load JS stayed at 102 kB against an 87.3 kB shared baseline. |
| 14a-7 | Placeholder strings in extracted text fields | **Whole-string placeholder rejection at the mapping boundary (`realValueOrNull`), the non-URL sibling of `httpUrlOrNull`.** Same root cause as #14a (schema-shaped ≠ real): `venue_address` is typed as a plain string, so "no address on this listing" came back as the literal `"N/A"` on 5 of 32 active rows. Being truthy, it survived every `\|\|` fallback and reached three surfaces at once — Google Maps destination, Uber dropoff, and the venue's `address` in the page's MusicEvent JSON-LD (i.e. junk published into structured data on a page whose whole purpose is search traffic). Nulling it restores the existing `"<venue name>, Austin, TX"` fallback, which is a real searchable destination. Matched as **whole strings only, never substrings**, so "Nada Surf" and "The Unknown" survive — regression-tested. Required fields (`artist_name`/`venue_name`) can't fall back to anything, so a placeholder there skips the row instead. 6 corrupted rows were patched in production. |
| 14a-6 | Uber deep link `client_id` | **Superseded — see #14a-11.** Registering a real Uber developer app and adding `client_id` was a necessary step (the Client ID is required by Uber's real endpoint), but it wasn't the actual bug — the endpoint itself was wrong. Real-phone testing after this change still showed no prefill, which led to #14a-11. |
| 14a-11 | Uber deep link endpoint was never a real one | **`buildUberUrl` was pointed at `m.uber.com/ul/?action=setPickup&dropoff[...]=...` — not a documented Uber endpoint at all.** It silently redirected straight to Uber's plain marketing homepage with nothing filled in, which is exactly the symptom reported (on desktop, and confirmed again on a real phone even after adding `client_id`). Uber's actual current Universal Deep Link (developer.uber.com/docs/riders/ride-requests/tutorials/deep-links/introduction) is `https://m.uber.com/looking?client_id=...&drop[0]=<url-encoded JSON>` — location is a single JSON object (`{latitude, longitude, addressLine1, addressLine2}`), not bracketed query keys, and there is no `action` parameter in the current scheme. Rewrote `buildUberUrl` to match the documented format exactly; verified via a direct request trace that the corrected link's `drop[0]` now survives the entire redirect chain to Uber's final page — the old link lost every parameter on the first hop. **A hard platform limitation remains, confirmed by Uber's own FAQ, not a bug in this app:** *"Can I set URL parameter to Deeplink into the mobile Uber website m.uber.com? No, the Deeplink and universal link features are designed for our native Uber app."* Prefill only happens if the Uber app is installed and the OS intercepts the universal link to open it natively — the logged-out mobile web page (what renders when the app isn't installed, or isn't intercepted) will never show prefilled fields, no matter how correct the URL is. Verified this directly: even the corrected, docs-matching link showed a plain empty "Dropoff location" field on the guest web page. **Still needs a phone test with the Uber app actually installed** — that's the one scenario this endpoint fix can actually help, and the one scenario nothing here could verify. |
| 14a-12 | Android opens Chrome instead of the Uber app | **Added an Android-only `intent://` path (`buildUberAppIntentUrl` + `components/live/UberLink.tsx`), keeping the https link as the default everywhere else.** After #14a-11 the URL was correct but a real Android device still opened Chrome rather than the app. Ruled out our own markup first by fetching Uber's own association files directly: `m.uber.com/.well-known/assetlinks.json` grants `com.ubercab` `handle_all_urls`, and the iOS `apple-app-site-association` lists `/looking` explicitly — so the domain-level setup is correct and the failure is Android's *per-device* App Link verification (or the user having turned "Open supported links" off for Uber), which no https URL can override. | 14a-10 | Concurrency limits for the weekday scrapes | **Measured directly against the real Firecrawl API before shipping, in two rounds, because the first design was wrong.** First attempt: scrape all 6 weekday days (8 pages total) fully concurrently via `Promise.all` — 6 of 8 calls blew past the 20s per-call timeout, because Firecrawl's own processing time degrades under concurrent load rather than each request just queueing cleanly. This app's cron runs on **Vercel Hobby, which hard-kills a function at 60s and drops the entire run** — not just the slow part, the previously-reliable today/weekend data too — so sequential didn't fit. Concurrency 2 (`mapWithConcurrency` in `sync.ts`) landed 49-59s across repeated real runs: fast enough on paper, but one run only completed 7/8 before a timeout, and 59s left almost no margin. | 14a-3 | Whole-card click target vs. nested interactive buttons | **A sibling `absolute inset-0` stretched link, not a wrapping `<a>`.** Wrapping the whole card in a link would nest the Directions/Uber `<a>` tags inside it — invalid HTML, unpredictable click targeting. The stretched link sits at a low z-index as a sibling; the two buttons get `relative z-10` to stay independently clickable; everything else (image, text) is plain static content, which a z-indexed positioned sibling paints over and correctly intercepts regardless of DOM order. | 14a-2 | "Today" boundary for /live | **9am-to-9am Chicago cycle, not midnight-to-midnight.** A show that started at 8pm was disappearing from "Tonight" the instant its start time passed, because `getUpcomingEvents` filtered `event_datetime >= now`. Fixed two ways: `isToday`/`formatEventDayLabel` (`lib/events/time.ts`) now key off a cycle that starts at 9am Chicago, so a show stays "Tonight" all night and only rolls over once the *next* day's sync has run, not at the clock's midnight; and the query's lower bound widened to a rolling 26-hour lookback so those events stay in the fetched result set at all, with the actual today/not-today call still made by the cycle-aware function downstream. | 14b | Intro video storage | **A pasted link embedded in an iframe, not an upload.** The old flow put a ≤30s/≤50MB clip in Supabase Storage, which capped every intro at 30 seconds and cost storage per profile, while most users already host their music video somewhere better. `profiles.intro_video_url` holds the raw pasted link; `lib/media/videoEmbed.ts` resolves it to an embed URL at render time (so the resolver can change with no data migration). Provider **allowlist**, not "iframe anything": (1) most sites refuse to be framed at all — Instagram, TikTok, and Facebook all block it, so a generic iframe renders a blank box; (2) profiles are public and user-controlled, so an arbitrary iframe would let anyone render a page of their choosing on splitmic.com — e.g. a fake SplitMic login form — which is a phishing vector no visitor could detect. YouTube (via youtube-nocookie), Vimeo, Loom, SoundCloud, Spotify, and Google Drive cover every real video platform. **A direct link to a video file (.mp4/.webm/.m4v/.mov/.ogv) is accepted from _any_ host**, because it renders in a native `<video>` element rather than an iframe — media bytes can't render HTML or run scripts, so the impersonation risk that motivates the allowlist simply doesn't exist for that case. That distinction (`VideoEmbed.kind` — `"iframe"` vs `"file"`) is the actual security boundary, not the host list. Dropbox share links are rewritten to serve the raw file and then travel the file path. http file links are rejected with an explanation, since a browser blocks mixed content and would otherwise render an empty player. Old `profile_media` rows with `kind = 'video'` are left in place, unread, rather than deleted. |
| 14 | Removing dead directory listings | **Soft-deactivate (`is_active = false`), not `DELETE`.** A free website check (`lib/directory/websiteCheck.ts`) classifies each listing `live`/`dead`/`uncertain`; only a non-resolving domain, refused connection, or hard 404/410 counts as `dead` — a timeout, TLS error, 5xx, or 403 stays `uncertain` rather than risk mislabeling a real, still-open business as gone.
